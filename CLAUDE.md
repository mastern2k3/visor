# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Visor is a cross-WM "attention HUD" for Claude Code sessions running on the same Linux machine. A long-lived daemon watches every live session and emits its state ("working", "waiting on user", "blocked on permission prompt") to a small dock pinned to the right edge of the screen — one drawer per session, color-coded, click to dismiss/jump. Single static Go binary.

The repo contains an experimental product in active iteration with one user — no release tag, no stability promise. Read the conversation context (or the user) before making sweeping changes.

Test coverage is uneven by design, not oversight. Seven packages have tests: `config`, `render`, `browse`, `x11`, `wlr`, `state`, `transcript`. `internal/hud/render` is the thoroughly tested one — it's pure pixel/geometry logic with no display server dependency, so it gets the deepest coverage (bleed regressions, welded-edge margins, elapsed/halo quantisation). The `x11` and `wlr` backends have pure-function tests only (animation math like `tickX`/`computeRightMargin`, not anything that opens a real X/Wayland connection) — there is no headless display server in CI (there is no CI) to exercise `newDock`/`Open`/`Close` against. `internal/discovery`, `cmd/visor/hook.go`, and the daemon's IPC wiring remain untested.

## Build & run

```
go build -o bin/visor ./cmd/visor

# install hook wrapper + print settings.json snippet for ~/.claude/settings.json
./bin/visor install

# run the daemon (foreground)
./bin/visor daemon [-v]

# query daemon state
./bin/visor ctl list                # table
./bin/visor ctl json                # JSON
./bin/visor ctl watch               # long-lived stream (used by the HUD)
./bin/visor ctl dismiss <id>
./bin/visor ctl ack <id>
./bin/visor ctl jump <id>           # warps focus via internal/focus (X11 + tmux)

# HUD — backend defaults to auto-detect: WAYLAND_DISPLAY set -> wlr, else x11.
# Override with --backend=x11 or --backend=wlr.
./bin/visor hud install
./bin/visor hud open
./bin/visor hud close

# palette theme and drop-shadow, persisted to $XDG_CONFIG_HOME/visor/hud.conf
# (falls back to ~/.config/visor/hud.conf); also settable per-invocation via
# --theme=<name> / --shadow=true|false on hud install/open/close.
./bin/visor hud theme <tuned|silent|traffic>
./bin/visor hud shadow <on|off>

# debug helper: classify a transcript without the daemon
./bin/visor ctl classify <path>.jsonl
```

The daemon listens on `$VISOR_SOCK` or `$XDG_RUNTIME_DIR/visor.sock`. Reads transcripts from `$CLAUDE_CONFIG_DIR/projects` or `~/.claude/projects`. State recovery file lives under `$XDG_STATE_HOME/visor` or `~/.local/state/visor`.

## Architecture in one breath

**Inputs.** Two streams of evidence feed the daemon:
1. Global hooks registered in `~/.claude/settings.json` (`SessionStart`, `Stop`, `UserPromptSubmit`, `Notification` with separate `matcher` entries for `permission_prompt` and `idle_prompt`, `SessionEnd`). The shell wrapper `scripts/visor-hook.sh` sets `CLAUDE_PID=$PPID` and exec's `visor hook <event> [--matcher ...]`. `cmd/visor/hook.go` enriches the payload with PID, WM info (via `internal/wm`), and tmux pane, then POSTs JSON to the daemon socket.
2. A file tailer (`internal/discovery`) using fsnotify on the projects root plus a 400 ms per-file mtime/size poll. New appends to `<project>/<sessionId>.jsonl` are decoded with `internal/transcript` and folded into the session store.

**Source of truth.** JSONL is canonical; hooks are low-latency metadata + the only way to learn about permission prompts (which never appear in the transcript). The Notification hook is the *sole* signal for `waiting=permission`.

**Classification.** `internal/transcript/classify.go`:
- last non-sidechain conversation line is `assistant` with `stop_reason="tool_use"` → **working**
- last is `assistant` with `stop_reason="end_turn"` → **waiting**
- last is `user` whose content has `type=tool_result` → **working** (model is processing)
- last is `user` otherwise → **waiting**
- Sidechain lines (`isSidechain: true`) and metadata types are skipped. Use `bufio.Scanner` with the **10 MB buffer** — tool results blow past the 64 KB default and silently truncate parses.

**State model.** `internal/state` has two orthogonal axes:
- *Activity* (objective, from JSONL/hooks): `working` / `waiting` / `unknown`.
- *Attention* (subjective): `ack` / `needs` / `dismissed`. Dismiss silences a session until the next transition; a working→waiting cycle re-arms `needs`. `Waiting` enum distinguishes `user` vs `permission`. Any subsequent live event for a dismissed session (hook or transcript append, but not startup backfill) clears the dismissal — silence is per-quiescent-period, not permanent.

`Snapshot` is what leaves the store — sorted by attention priority (needs > ack > dismissed), then by `FirstSeen`, so HUD tabs do not reshuffle on every update. `display_cwd` is computed server-side (`$HOME → ~`) so backends don't need home-dir logic. Three more server-computed fields feed the redesign's rendering: `display_name` (the project/title label shown on the panel), `glyph` (a one-or-two-character avatar, collision-disambiguated across concurrent sessions — see `assignGlyphs`), and `state_since` (when `Activity`/`Waiting` last transitioned, used to render elapsed time).

**Pub/sub.** `internal/state/notify.go` broadcasts a fresh `Snapshot` after every mutation. A SHA-256 digest of *only HUD-observable fields* (id, activity, waiting, attention, display_cwd, title, background fields, and `glyph`) suppresses no-op broadcasts — this is why push-driven backends (`visor ctl watch`, and the in-process x11/wlr renderers) don't repaint on every no-op tick. `Glyph` is in the digest deliberately: it's low-frequency (only changes when a session's title-derived initials collide with another live session) but is HUD-observable, so excluding it would let a glyph change go unpainted. `LastUpdate` and `StateSince` are **not** in the digest — both change far more often than anything visible, and `StateSince` in particular doesn't need to be: it only moves alongside `Activity`/`Waiting`, which are already digested, so including it would add nothing but reintroduce the flicker. **Never widen the digest with a field like `LastUpdate`.**

**IPC.** `internal/ipc` — one JSON request per line over a Unix socket, one response back. A `Response.Stream` channel switches the server into long-lived line-streaming mode (used by `watch`). `ipc.Call` is one-shot; the `watch` ctl handler dials directly to keep the connection open.

**HUD backends.** `internal/hud/hud.go` defines a minimal `Backend` interface (`Name / Install / Open / Close`). Two implementations, both pure-Go, in-process, and push-driven off `internal/state`'s pub/sub: `x11` (native dock via `jezek/xgb` + `xgbutil` — one override-redirect window per session) and `wlr` (native Wayland dock via `codeberg.org/tesselslate/wl` + locally-generated `wlr-layer-shell-unstable-v1` bindings in `internal/hud/wlr/protocol/` — one `zwlr_layer_surface_v1` per session). Both share pixel drawing via `internal/hud/render`: an antialiased capsule tab that shows `CapsuleW` (18px) at rest with the rest of its `CapsuleDrawW` draw width hanging off-screen as protrusion budget for the breathe/alert offsets, a two-line neutral hover panel (line 1 name; line 2 state-words · elapsed · path), no in-capsule background-work indicator (background work animates the tab instead), and three switchable palette themes (`tuned`/`silent`/`traffic`, see `internal/hud/render/palette.go`). Compositor coverage for `wlr`: Niri, sway, hyprland, river, wayfire, labwc, KDE. GNOME has no layer-shell — use `--backend=x11` (via XWayland) there. `cmd/visor/hud.go::pickBackend` is the registry and also does auto-detection (empty `--backend` → wlr if `WAYLAND_DISPLAY` is set, else x11) — add a new package under `internal/hud/<name>/`, implement Backend, and add a case. Do not widen the interface until a new backend needs a method neither existing one has.

**Tab clicks (x11 backend).** Left = `jump` (focus dispatch), right = `dismiss`, middle = `ack`. See `internal/hud/x11/tab.go::onButton`.

**Armed browsing.** `internal/hud/browse` holds the rule deciding which tab is expanded as the cursor moves, shared by both backends and free of any display-server dependency (so it is unit-tested deeply, like `render`). Two states: *disarmed*, where only the tabs' own edge strips are sensitive and a hover expands immediately; *armed* — entered by that first hover — where the whole `BufW`-wide column becomes row-sensitive so moving straight down swaps panels without travelling back to the screen edge. Row swaps have **no dwell** — the row holding the cursor is the row that is open, immediately, in both states. An earlier draft gated swaps behind a 70ms intent timer to stop a diagonal exit sweep from flashing every crossed row open; that cost was perceptible on every deliberate row change (70ms dwell plus up to 33ms of animation-tick granularity, since the deferred commit piggybacked the 30Hz ticker) and the flicker it prevented was never measured — the edge strips have always popped instantly with no dwell and read fine. Do not reintroduce a swap delay without evidence the flicker is actually objectionable. The one delay that remains is `DisarmGrace`, a debounce on *disarming*, needed only by wlr: its `wl_pointer.leave` carries no coordinates, and adjacent surfaces are separated by a 10px insensitive shadow-pad band, so an ordinary row crossing produces leave-then-enter ~1ms apart that must not read as "left the dock". It is resolved on wlr's 20Hz loop via `Tracker.Tick`; a late disarm is invisible. x11 needs none of it — its crossings carry root coordinates, so `Contains` decides exits synchronously and `Tick` is never called there. Backends feed it events and apply the `browse.Action` values it returns; they never reimplement the rule. x11 senses the inland cursor with one InputOnly catch window *per row* (`internal/hud/x11/catch.go`, reconciled by `dock.syncCatches`) because an XShape input region is clipped to its own window and a collapsed tab's window is mostly off-screen right — it physically cannot see a cursor 300px inland. Per-row rather than one column-spanning window, and Enter/Leave rather than motion, for the event-volume reason in Things That Will Bite You below; entering a window *is* the row identification, so there is no coordinate hit-testing. wlr needs no such thing: its surfaces are already `BufW` wide in contiguous y bands, so arming just widens the collapsed ones to `regionFull` and the compositor's own pointer focus does the row hit-testing. Design notes: `docs/superpowers/specs/2026-08-11-armed-tab-browsing-design.md`.

**Focus dispatch.** `internal/focus` warps the user back to a session. Two best-effort steps run in order: (1) EWMH `_NET_ACTIVE_WINDOW` ClientMessage to the captured X11 `WindowID`, (2) tmux `select-window` / `select-pane` against the captured `TmuxPane`. Either step is skipped if its locator wasn't captured at SessionStart. The daemon's `jump` IPC handler in `cmd/visor/daemon.go` builds the `focus.Target` from the session and calls `focus.Dispatch`. Wayland-native focus (Niri, sway, hyprland) is not yet wired — currently relies on the X11 path working under XWayland or the WM honoring EWMH.

**HUD config seam.** `internal/hud/config` resolves the two user-facing HUD preferences — palette theme and drop-shadow — from a flat `key = value` file at `$XDG_CONFIG_HOME/visor/hud.conf` (falling back to `~/.config/visor/hud.conf`). `Resolve(flagTheme, flagShadow)` applies `flag → env (VISOR_THEME/VISOR_SHADOW) → file → default` precedence and never fails — a missing or malformed file just degrades to defaults. `Watch` fsnotifies the file's *parent directory*, not the file itself, because `Save` replaces the file's inode on every write rather than editing in place, which would otherwise orphan a direct-file watch after the first save. Each backend's dock consumes `Watch`'s update channel and calls `applyConfig` to re-render every tab in place with the new palette/shadow — no restart needed. Passing `--theme` or `--shadow` to `hud install|open|close` pins the *whole* resolved config (both theme and shadow together) for the process's lifetime and skips starting the watcher at all, so a later `visor hud theme`/`visor hud shadow` write can't silently override either flag mid-session.

## Things that will bite you

- **Hooks must stay silent on failure.** Anything written to stderr is logged by Claude as a warning. `visor hook` already treats "daemon not running" (ECONNREFUSED / ENOENT / ECONNRESET) as expected and silent; preserve that behavior or you will spam the user's session log.
- **Map iteration is randomized.** `Snapshot()` sorts the slice before returning. If you add a new entry path that bypasses it, the HUD will reshuffle every refresh.
- **Why the x11 backend exists instead of eww (retired).** eww, the original backend, had no input-shape / passthrough option in 0.6.0 (verified by reading `crates/yuck/src/config/backend_window_options.rs` — only `sticky`, `struts`, `windowtype`, `wm-ignore`), and GTK doesn't auto-apply XShape from alpha there either. That gap is what native `x11`/`wlr` backends were built to close.
- **Depth-32 X windows need an explicit `CwBorderPixel` *and* `CwColormap`.** Inheriting the root's colormap on a 32-bit ARGB visual yields `BadMatch`. See `internal/hud/x11/argb.go::newARGBWindow`.
- **`xgbutil/xgraphics` cannot make depth-32 pixmaps.** Its `CreatePixmap` hardcodes `X.Screen().RootDepth`, so per-pixel-alpha upload has to go through a raw depth-32 pixmap + `PutImage` instead (`internal/hud/x11/argb.go::uploadRGBA`).
- **Shape the input region, not the bounding region.** Setting the XShape *bounding* region would make a compositor's shadow follow the capsule's rounded outline, but a bounding region hard-clips rendering and turns the antialiased corners into stair-steps. Only the *input* region is shaped, so clicks on the transparent shadow padding fall through without touching what gets drawn.
- **`MaxProtrusion` is exactly tight, not generous.** A `needs` tab at breathe peak consumes the entire off-screen overhang budget (`AlertProtrusion + max(WobbleAmp, WorkBreatheAmp)`). Raising either `AlertProtrusion` or `WorkBreatheAmp` in `internal/hud/render` without also raising `MaxProtrusion` reintroduces a visible gap between the capsule and the screen edge at peak breathe.
- **All tab motion goes through `render.MotionOut`, and background work is signalled by motion, not pixels.** Two motions, mutually exclusive, and **the wobble overrides**: `activity=working` wobbles fast (`WobbleAmp`/`WobblePeriod`), and *only* when not working does background work breathe slow (`WorkBreatheAmp`/`WorkBreathePeriod`). A working session with a shell open therefore reads as plain "working" — superimposing both produced a compound motion that was harder to read than either alone. Because only one term ever applies, the overhang budget covers `max(WobbleAmp, WorkBreatheAmp)`, not their sum. Both backends route through the one function so they cannot drift. **Background work is never drawn into the buffer at all** — not while running, not as an outcome; there is a test asserting a tab's pixels are identical regardless of background state. It animates the window instead, because `win.Move`/`SetMargin` is free and smooth at the full tick rate where an in-buffer animation is capped at `HaloSteps` per `HaloPeriod` (~5fps) by re-render cost.
- **`xevent.Quit` only sets a flag, and the wake-up event has to be addressed to us.** xgbutil's `mainEventLoop` checks the flag once per iteration, at the top, then parks in `Read`/`WaitForEvent` — so the flag alone changes nothing, and some event must arrive *on this connection* to return from the read. `dock.quit()` does that by sending a ClientMessage to `X.Dummy()` with an **empty event mask**, which X routes to the client that created the destination window regardless of what that client has selected. It previously sent to the root window with `EventMaskStructureNotify`, which only reaches clients that have selected `StructureNotify` on root — and this one never has (root is used solely as a `CreateWindow` parent). The wake went nowhere, so SIGTERM logged "shutting down" and then hung forever: SIGKILL was the only way to stop the HUD, and `close()` never ran. If you add another shutdown path, mirror the empty-mask-to-own-window form, and verify it end to end (`kill -TERM` should log "event loop quit" and exit in ~200ms, leaving zero `visor-tab` windows) — the failure mode is silent.
- **PID capture happens in the hook wrapper.** `$PPID` in `scripts/visor-hook.sh` is the claude process. If you ever invoke `visor hook` differently, set `CLAUDE_PID` explicitly or this metadata is lost.
- **Backfill discovery filters by `mtime > 24h ago`** to avoid storming the daemon with historical transcripts. Active sessions older than 24h get picked up only when something appends to their JSONL or a hook fires.
- **wlr buffer ownership.** The compositor owns each `wl_buffer` from `attach`+`commit` until it sends `wl_buffer.release`. Reusing a buffer earlier corrupts pixels silently. `internal/hud/wlr/buffer.go` tracks a `released bool` per buffer; never bypass it. The Wayland dispatch goroutine is the single mutator — calling `Acquire()` from another goroutine would need synchronization.
- **wlr dispatch loop is a 20Hz poller, not edge-triggered.** `tesselslate/wl` doesn't expose the display fd, so `dock.run()` uses a rate-limited `wl_display.sync` wakeup to bound `Dispatch()` latency. Snapshot updates interrupt the sleep, so user-visible latency stays low. Proper fix would be vendor-patching `tesselslate/wl` to expose `Display.Fd()` and switching to `unix.Poll`.
- **The 30Hz animation tick must not `DrawTab` a collapsed, non-permission tab.** This is the load-bearing performance invariant of the redesign: an unoptimised triple box-blur per render is only affordable because most ticks do zero rendering. The tick itself (`dock.animate`/the wlr equivalent) only *repositions* windows/surfaces; re-rendering the pixel buffer is gated behind three separate early-return guards spread across two files — `tab.go::tickElapsed` returns immediately unless the tab is expanded (hovered), `tab.go::tickHalo` returns immediately unless the current state is a `Glow` state (permission only), and neither is called from the position-only tick path at all except through those guards. If you add a per-frame `DrawTab` call, or loosen either guard, every tab in the dock repaints 30 times a second regardless of visibility — do not do this.
- **Never make a checked (synchronous) X request from inside an xevent callback.** It deadlocks the entire dock — permanently, with no log line and no response to SIGTERM. The callback blocks waiting for its reply; xgb's reader goroutine is blocked pushing an event into its 100-slot `eventChan`; the only drainer of that channel is the goroutine stuck in the callback. Circular wait. This is why `setInputRegion` uses unchecked `shape.Rectangles` and why every mutator in `catch.go` is unchecked — see the comments at both sites. It was latent for as long as `setExpanded` has existed and only became reachable when armed browsing started generating enough events to fill the channel. Diagnose it with `kill -QUIT <pid>`: goroutine 1 parked in `dock.run` plus `xgb.readResponses` in `[chan send]` is the signature.
- **`EventMaskPointerMotion` is effectively unusable in this dock.** Motion delivers hundreds of events per second, which saturates `eventChan` and makes the deadlock above fire almost immediately. This is why armed browsing uses one InputOnly catch window *per row* with Enter/Leave only, instead of one column-spanning window that would need motion to notice row changes: a row change costs one Leave plus one Enter, and the row is identified by *which window* was entered rather than by hit-testing a coordinate.
- **`StackModeBelow` without a `Sibling` means the bottom of the *global* stack**, beneath every other application's windows — not beneath visor's own. A catch window stacked that way receives pointer events only where nothing else covers it, which on a populated desktop is nowhere; the cursor inland lands in whatever terminal or browser is under the dock, and browsing silently does nothing while hover at the edge still works. Each catch window is therefore stacked `Below` its own row's tab window *as an explicit sibling* (`catchWindow.stackBelow`), which is sufficient because rows occupy distinct y bands so a catch window overlaps exactly one tab. Verify this kind of thing with `xdotool getmouselocation --shell`, which reports the window actually under the pointer.
- **A tab's `LeaveNotify` can never be read as "left the dock" on its own.** Most crossings are not exits: expanding a tab slides its window under the cursor (Leave on the catch window, Enter on the tab), and every row change produces a Leave too. Both leave handlers test `tracker.Contains(ev.RootX, ev.RootY)` first. Relatedly, the overflow tooltip is given an *empty* input region — it sits in the row above its tab and would otherwise swallow that row's Enter.
- **`argb` is latched once in `newDock` and cannot be changed after `CreateWindow`.** It determines the X window's *depth*, which X11 fixes at creation time, so there is no way to "notice" a compositor arriving later and re-derive it in place — the value is resolved once (`visualOK && hasCompositor(X)`) and lives for the process's lifetime. The real exposure: if the HUD autostarts a moment before the compositor does (a common race at login), `argb` latches `false` and the whole session degrades to squared corners with a black shadow pad (see the `!argb` black-column entry in Pending/known WIP) — with no recovery path and no repeated log line to notice it by, just the one `"no compositing manager or ARGB visual"` line at startup.

## Conventions

- The hook wrapper has a working copy in `scripts/visor-hook.sh` *and* an embedded copy in `cmd/visor/install_hook.sh` — keep them in sync (the build script `cp`s; CI doesn't exist yet).
- The `_refs/` directory holds upstream projects we cribbed parsing patterns from (`ccdiag` for JSONL types, `claude-pool` for hook scripts). It's gitignored; do not import from it.
- Logging uses `log/slog`. Hook command exits 0 on every path (Claude blocks on the hook's exit code).

## Pending / known WIP

- Focus dispatch covers X11 (EWMH) + tmux. Niri / sway / hyprland native focus protocols are not yet wired — under those compositors, jump relies on XWayland or the WM honoring EWMH. Add per-WM adapters in `internal/focus/` when needed; the `WM` field on `focus.Target` is the dispatch key.
- **The `wlr` backend is unverified on hardware.** It was developed and reasoned about (protocol bindings, buffer lifecycle, dispatch loop) but never actually run under a layer-shell compositor. Its first real run under Niri/sway/etc. deserves a specific check of the resting visible capsule width — that's the geometry most likely to be off if an assumption about the compositor's anchoring/margin behavior doesn't hold in practice.
- **One window for the whole dock, instead of one per tab.** Considered and deferred while building armed browsing, which it would have made nearly free (the dock window is already inland, so `MotionNotify` on it gives the row directly and `catch.go` would not exist). It would also unpin `RowPitch == BufH` — that constraint exists only so each shadow fits inside its own window — allowing closer tabs with blended shadows. The blocker: one window per tab is what makes animation free. Wobble and breathe today are `win.Move`, zero drawing and zero upload, which is exactly why the 30Hz tick can run with `DrawTab` gated off; in a single window it becomes a redraw plus re-upload of that strip, so three moving tabs cost 3 `DrawTab` (blur included) and ~216KB per frame against today's zero. Recoverable by caching each tab's RGBA and `memcpy`-ing it at the motion offset with damage-rect uploads (the breathe is pure translation), but that is hand-writing a compositor to replace the one X already provides. Revisit when something genuinely needs to span rows: overlapping shadows, a panel taller than its row, a dock header/footer, or drag-to-reorder. `catch.go` is ~30 lines and gets deleted by that refactor with nothing stranded. Trade-off written up in `docs/superpowers/specs/2026-08-11-armed-tab-browsing-design.md`.
- **The x11 `!argb` fallback renders a black column, not a clean squared tab.** `DrawTab` always leaves the `ShadowPad` region transparent, even with `Square` set — `Square`/`Shadow` only change how the capsule's own corners/shadow are drawn, not the pad around it. Uploaded at root depth (no compositor), that alpha is discarded on upload and the transparent (== premultiplied black) pad pixels land on screen as opaque black; because `RowPitch == BufH`, every tab's pad abuts the next one's, so the whole dock shows an unbroken black stripe down its screen-edge side. This is a regression versus the pre-redesign renderer, which filled the entire buffer with the opaque state colour and had no transparent region at all. Known and intentionally not fixed in the visual-redesign branch — see the comment at the `Square`/`Shadow` decision site in `internal/hud/x11/tab.go::tabState` and the documenting-not-endorsing test `TestDrawTab_SquareStillLeavesPadTransparent` in `internal/hud/render/tab_test.go`. A real fix likely means making the pad opaque-state-colour instead of transparent whenever `!argb`, in `DrawTab` itself.
